5. 后续阶段也是一次只执行一个阶段，完成并通过验收后等待我的继续指令。
6. 每个阶段内部允许长时间自主工作，不需要每完成一个文件就询问我。
7. 不允许通过同时启动多个智能体来并行推进。
8. 不允许省略测试，不允许使用虚假的成功日志，不允许把未实现的功能标记为完成。
9. 遇到可以自主解决的技术问题，先搜索、分析、修复和重新验证，不要轻易停止。
10. 遇到API密钥、账号授权、人工报名等必须由我处理的事项，列出阻塞项；其他不依赖它的任务继续推进。
11. 不要因为模型上下文不足就放弃。持续将阶段进度、架构、已完成事项、问题和下一步写入项目文件，以便恢复工作。

三、第一阶段：完整全栈网站开发

这是当前唯一允许执行的阶段。

项目暂定名称：

SkyRoute AI · 天气智运与增长决策平台

可以优化产品品牌名称，但必须清楚区分两个赛题。

目标是开发一套具有现代化企业级视觉风格、能够真实交互和运行的全栈Web应用。

不是静态PPT式网页，不是简单聊天机器人，也不是只能点击菜单的空壳。

3.1 技术架构

建议技术栈：

前端：

- React
- TypeScript
- Next.js或Vite
- Tailwind CSS
- shadcn/ui或其他成熟组件库
- ECharts或Recharts
- 适当使用Framer Motion等动画方案

后端：

- Node.js + TypeScript API，或Python FastAPI
- 清晰的REST API
- Pydantic或Zod数据校验
- 完善的输入校验、异常处理和运行日志

数据库：

- SQLite，优先保证零配置本地运行
- ORM可选择Prisma或SQLAlchemy
- 提供数据库初始化和种子数据脚本

AI能力：

- 支持OpenAI兼容API的可配置模型调用
- 支持环境变量配置API Key、Base URL和模型名称
- 不在前端暴露密钥
- 无模型API时使用真实可执行的规则决策引擎，并明确标记为规则模式
- 不得把固定模拟回答伪装成真实大模型推理

测试：

- 单元测试
- API测试
- 端到端浏览器测试
- 构建与类型检查
- 关键业务结果正确性测试

上述方案是建议而不是限制。可以根据实际运行环境选择更稳定的技术组合，但必须说明选择理由。

优先保证可以本地一键启动、两道赛题功能完整、演示稳定。不要为了技术复杂度而引入不必要的微服务或云基础设施。

3.2 全站视觉要求

网站设计必须达到优秀竞赛作品的展示水准。

风格定位：

- 现代化物流科技SaaS平台
- 企业级管理驾驶舱
- 简洁、专业、具有视觉冲击力
- 兼顾科技感和真实业务工具的可读性

设计要求：

1. 有统一的设计规范、颜色、字体、图标和组件。
2. 默认使用深色科技风，但核心信息必须清晰可读。
3. 卡片、图表、按钮、导航、弹窗等风格一致。
4. 必要的加载状态、错误提示、空数据状态齐全。
5. 支持桌面浏览器，兼顾手机和较小屏幕。
6. 提供适度的交互动效，避免无意义动画拖慢演示。
7. 全部核心功能都有明显的操作入口。
8. 避免廉价模板感、装饰性乱码、占位按钮和无功能菜单。
9. 界面主要使用简体中文。
10. 数据图表必须有清晰单位、来源及必要的模拟数据标识。

可以根据需要自行设计原创图标和视觉元素，但不要未经授权盗用其他平台商标或声称获得官方认证。

模块B：气象物流风险预警智能决策系统

这是网站最重要的技术模块。

至少包括：

B1. 物流运输总览

展示：

- 运输订单
- 运输走廊
- 重要节点
- 运输状态
- 风险等级
- 预计延误
- 风险订单统计

指标与底层数据必须能够对应。

B2. 运输网络地图

选择北京—天津区域运输走廊，或优先采用官方指定网络。

使用节点和边构建网络模型，明确不同路径的可达性。

在地图中展示运输节点、线路、天气风险和推荐方案。

地图上的几何连线仅用于可视化时必须明确标识，不得把直线距离当作真实公路里程。

B3. 天气数据与风险预警

输入或加载：

- 降雨
- 降雪
- 大风
- 能见度
- 温度
- 天气预警信息

可以选择不同恶劣天气场景。

允许使用明确标注的模拟天气数据，并提供数据来源与假设说明。

B4. 运输订单管理

订单字段至少包含：

- 订单编号
- 起点和终点
- 货物种类
- 重量或货量
- 发运时间
- 承诺送达时间
- 优先级
- 原计划路线
- 原计划成本及运输时间

提供新增、编辑、筛选和查询功能。

B5. 风险分析引擎

系统应根据天气、路径、货物特征、交付时间和运输限制计算风险。

应提供：

- 风险等级
- 风险原因
- 影响区段
- 受影响订单
- 可能延误
- 评估依据

风险模型需要可解释，不能随机生成一串看似精确的结果。

B6. 多方案决策优化

至少提供：

方案一：原计划运输。

方案二：提前发运。

方案三：绕行。

方案四：调整中转节点。

对于不能适用的方案，应给出不适用原因。

每个可行方案都要计算：

- 运输时长
- 到货时间
- 延误风险
- 运输成本
- 额外成本
- 剩余风险
- 预计准时表现

允许调整成本、时间和风险的决策权重。

必须确保推荐方案来自真实执行的计算逻辑。

B7. AI智能体分析

实现具有明确工作流程的分析智能体。

建议流程：

获取任务 → 读取数据 → 识别风险 → 调用算法工具 → 生成备选方案 → 计算对比 → 输出建议。

保留工具调用记录、输入与输出。

有配置的大模型时，可以负责自然语言解释、用户提问和方案总结，但不能在没有算法依据时随意编造成本、路径或延误数值。

无模型API时，系统仍要通过规则引擎完成决策，并明确展示当前工作模式。

B8. 情景仿真和历史回放

提供至少3种演示场景：

- 正常天气
- 暴雨导致运输风险提升
- 暴雪或大风影响多个运输节点

可以一键切换、运行并展示结果变化。

支持比较优化前后的：

- 准时率
- 平均延误时间
- 总运输成本
- 额外成本
- 高风险订单数量

注意实验假设、种子数据和结果必须可复现。

B9. 决策报告

生成包括订单信息、天气情况、风险分析、方案对比、推荐原因和关键指标的报告。

支持下载或打印。
